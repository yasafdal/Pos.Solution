# Z-Reading manual deployment and integration

## Status and safety boundary

Z-Reading is **off by default** (`ZReading:Enabled=false` when absent). No API startup/DI modification or automatic migration is required by this feature. Disabled service methods return before querying any new table. Deploying the new binary alone does not require Z tables.

The internal Z sequence is a report sequence, **not** a BIR accreditation, registered machine reset counter, or certification of this format. `ResetCounter` remains null/unknown; setup must not invent one. Branch currently has no stored TIN, so `Tin` remains null. Historical cumulative gross must be explicitly evidenced, never calculated from an arbitrary partial history.

No SQL here has been executed against an application database during implementation. SQLite tests establish sequential functional behavior only; PostgreSQL locking, SQL triggers, isolation, and actual printing require separate controlled acceptance tests.

## Deployment order (DBA/operator only)

1. Back up the database and reconcile every device that has used each terminal. Archive/audit pending, failed, conflict, retrying, and unknown-commit payloads; **do not delete them** to make readiness pass. Stop writes during deployment.
2. Review and execute `z-reading.sql` explicitly. It creates only new state/snapshot/print-audit tables, indexes, validation and immutable-history triggers. `IF NOT EXISTS` supports repeat installation; incompatible pre-existing tables still require catalog review, not silent column coercion. It does not modify any invoice/order sequence or insert a terminal baseline. It retains exact JSON text so SHA-256 is stable.
3. Review and execute **`z-reading-period-guards.sql`** as a mandatory companion. It must provide `public.pos_z_lock_terminal(integer)`, lock the same `Terminals` row, and **UPDATE `ZReadingTerminalStates.MutationVersion`** for protected fiscal writers. Generation checks function installation via `to_regprocedure` before readiness allows generation and invokes this function before aggregation. A lock without the shared UPDATE does not invalidate a stale SERIALIZABLE transaction snapshot. Review installed trigger coverage/enablement and permissions; presence of a function alone cannot prove that all triggers remain installed. Do not enable generation after installing only the core script.
4. Copy/review `z-reading-terminal-setup.sql` and fill the terminal ID, first business date, independently verified opening accumulated **gross** sales, and verification reference. It intentionally raises until all required values are explicit. Matching repeats are no-ops even after reports exist; mismatching repeats abort. It cannot overwrite state or fabricate/reset a fiscal counter. Internal `LastZNumber=0` means no report from this implementation exists yet, not a fiscal reset. The opening amount covers gross before the configured first date. Choose a first date only after reconciling prior events and source availability.
5. Grant the API role only needed SELECT/INSERT on immutable history and SELECT/UPDATE on terminal state. Do not use a table-owner/superuser role that can disable triggers. Baseline setup is an operator privilege, not an API endpoint. Retain all history and do not provide a destructive down script.
6. Deploy the client and server guards together, then opt in with `ZReading:Enabled=true`. Readiness requires the provisioned state, sequential dates (including zero-sales days), ended business period, and no known server blockers. Ensure claim scoping and device assignment before first generation.

The EF model snapshot was regenerated using the design-time factory only (no connection or API startup); the throwaway generated migration is outside the repository. The supported production deployment is the explicit manual SQL pair, not `Database.Migrate`. The manual SQL does not invent an EF history row. Future EF migrations must account for this manual baseline and never drop fiscal audit tables.

## HTTP contract

Base: `api/z-readings`. Authenticated roles: `Admin`, `Manager`, `Senior Cashier`, `SeniorCashier`. Plain cashier/PIN bypass is not supported. Admin can view authorized terminal history globally; every other role requires a matching `branch_id`; senior cashier additionally requires matching `terminal_id`. **Generation always requires the authenticated current `terminal_id`, including Admin/Manager**. If terminal has a registered `DeviceIdentifier`, generation requires exact match. Operator comes from the token, never the body.

- `GET terminals`: scoped `ZReadingTerminalDto[]`.
- `GET readiness?terminalId=1&businessDate=2026-10-29`: `ZReadingReadinessDto` with `Enabled`, `IsReady`/`CanGenerate`, `Blockers`, `Warnings`, `AlreadyGenerated`, `ExistingReportId`, `NextBusinessDate`, and UTC boundaries. Readiness is advisory, rechecked transactionally at generation.
- `POST generate`: `GenerateZReadingRequest`: `TerminalId`, `BusinessDate`, stable nonempty `ClientOperationId` (<=100), `DeviceIdentifier` (<=100), **`AllLocalOutboxesDrained=true`, `NoUnresolvedLocalTransactions=true`, `SoleDeviceCompletenessConfirmed=true`**. A pending-count boolean alone is insufficient. Returns the immutable `ZReadingReportDto`. Same exact operation returns original snapshot; operation reused for a different terminal/date/operator/device conflicts. Same terminal/date with another operation returns the already-stored report without advancing sequence.
- `GET by-date?terminalId=1&businessDate=2026-10-29`: immutable report or 404. SHA-256 verified before return.
- `GET {reportId}/print-attempts`: saved `ZReadingPrintAttemptDto[]`, ordered by start time. Includes `Id`, `Status`/`Outcome`, `StartedAt`/`CreatedAt`, `RequestedBy`, `ErrorMessage`/`Detail`, `Reason`, `IsReprint`, saved `Report`, `SnapshotSha256`. Unfinished entries remain `STARTED` after restart and are not automatically resumed.
- `POST {reportId}/print-attempts` (alias singular `print-attempt`): `StartZReadingPrintRequest` with stable **`ClientOperationId`**, `PrinterName`, `Reason`. Returns a persisted STARTED attempt plus immutable snapshot. Reprints (including after an unresolved STARTED) require reason. Retry of exactly the same operation does not create an extra attempt; do not auto-print after recovering an ambiguous start response.
- `POST {reportId}/print-attempts/{attemptId}/complete` (alias singular `print-attempt/{attemptId}/finish`): `CompleteZReadingPrintRequest` with **`Status`** (`ACCEPTED`, `FAILED`, `UNKNOWN`) and **`ErrorMessage`**. Only original operator can complete. Completion is a separately appended row, never mutation of STARTED. Same exact completion is idempotent; different result conflicts. ACCEPTED means print-subsystem accepted, not paper delivered. Dialog fallback/unknown outcome uses UNKNOWN.

All IDs for saved reports/attempts are GUIDs. Service API is `ZReadingService(PosDbContext, IConfiguration)`; `BusinessDate(DateTime utc)` and `Period(DateOnly)` are public static helpers. Readiness service `ReadinessAsync`; report `GenerateAsync` and `GetAsync`; printing `PrintAttemptsAsync`, `StartPrintAsync`, `CompletePrintAsync`. Feature-gated EF/API period guards should not query absent Z tables while disabled. EF snapshot and print audit UPDATE/DELETE protection runs without a database query and is not a substitute for deployed writer triggers (bulk/raw SQL bypasses EF).

## Accounting and scope

- Fixed Asia/Manila 04:00 cutoff: UTC start is prior calendar day at 20:00; `[start,end)` semantics. Never depend on host timezone. Stored legacy timestamps are interpreted under existing UTC storage convention; reconcile any imported local-time data before setup.
- Sales use stored invoice issuance timestamps and item names/values, not today's catalog or mutable X-reading aggregates. Refunded/voided payment flags do not erase original collections. Paid records lacking invoice issuance evidence block finalization rather than being guessed into a period.
- Gross is stored order subtotal; discounts are separate. `VatAdjustment = subtotal - discounts - total` captures statutory VAT removal/legacy residual. Net is sale total minus completed return events minus remaining void reversal. Cashier net uses authoritative order total (so it includes residual VAT adjustment implicitly). Returns are attributed to completed return time; voids to actual void time; processors receive adjustment attribution and original order/invoice references remain in `Adjustments`.
- Collections use payment entry event time and payment `Amount` (not tendered cash/change). Split tenders count entries. Completed refund entries are separate event-period outflows; they are not subtracted twice from sales. A void after prior returns subtracts remaining reversal only.
- `Products.Value`/`VoidProducts.Value` are gross stored line values; return product value is actual stored refund amount. Decimal quantities are preserved. `ExemptProducts` is the subset with stored EXEMPT VAT type. Void product detail includes original voided lines and may exceed remaining financial reversal after an earlier partial return; adjustment amount is authoritative.
- Order VAT totals are authoritative. Historical per-item VAT/return allocation provenance is not guaranteed; `HistoricalItemVatPrecisionAvailable=false` and warnings disclose this rather than recomputing from current product taxes.
- Opening float, expected drawer balance and actual count remain **per shift**; do not sum handoffs into a fake terminal-day float. Completed-period reconciliation blocks cross-period shifts. Accumulated gross advances only by gross sales, never by float/movements and never resets during printing.
- API cannot see another device's local SQLite/outboxes, so sole-device completeness is an explicit operator assertion, not a cryptographic guarantee. Client must drain all queues and lock local writes across finalization. Late new writes/replays must conflict via period guards while retaining payloads; exact already-acknowledged replays may return their existing ACK without new mutations. Cross-day returns are new adjustment events, not snapshot rewrites.

## Verification

Functional console suite: `dotnet run --project POS.Tests/POS.Tests.csproj` (isolated output directory recommended on Windows). Tests seed only in-memory SQLite with real transactions and verify fixed boundary, no invented baseline, idempotent zero-sales snapshot/sequence, immutable audit, adjustment event attribution, decimal products, split payment/refund separation, strict scope, disabled absent-schema paths, sequential dates and shared state fence. Existing source/package warnings are not introduced by the feature.

Before real enablement, separately test PostgreSQL two-connection races (sale/payment/offline/shift/cash/return/void/refund vs generation) under READ COMMITTED and SERIALIZABLE, idempotent script reinstall, trigger update/delete/truncate rejection, old ACK/no new late upload, function/trigger removal readiness failure, and printer failures/restarts. None of these PostgreSQL or hardware claims follows from SQLite tests.
