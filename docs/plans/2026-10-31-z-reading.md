# Z-Reading implementation plan and approved design

> Use test-first changes and isolated tests; never contact the application database, execute deployment SQL, print, or alter invoice/reset counters during implementation.

## Approved scope

One immutable report per terminal/business date (Asia/Manila, 04:00 local inclusive to next 04:00 exclusive). Supervisor-only, online-only generation after shifts and synchronization are complete. Printing is independent of generation. Include product, VAT-exempt-product, payment, discount, and cashier detail. Preserve blind-close redaction. Do not require an X-Reading print first.

## Safety and accounting decisions

- Opt-in API configuration `ZReading:Enabled`; default disabled. Explicit operator-provisioned terminal setup defines first report date and verified opening accumulated gross sales. Never fabricate a historical cumulative balance or seed a reset counter; display unconfigured reset counter honestly. Internal Z numbers are report sequence numbers, not evidence of BIR accreditation.
- Stored snapshot JSON plus SHA-256, unique terminal/date and client-operation ID, monotonic terminal report sequence, immutable report body; append-only print attempts separately. Sequential business dates, including explicit zero-sales days, prevent cumulative gaps.
- Date attribution uses invoice issuance/payment event for sales, actual completed return/void event for adjustments. Historical refunded payments still count as original collections; subtract adjustment once in its event period. Stored historical item names and amounts, not today's product/pricing.
- Product detail is gross line amount; discounts and residual VAT adjustment reconcile to order totals. Cashier sales belong to original sale cashier; return/void adjustments belong to processing user and retain original order references. Payment counts mean payment entries (split tenders are not item quantities).
- Drawer detail stays per shift. Never sum opening floats as one terminal-day float or double-count handoffs. Cross-period shifts block generation pending reviewed close/handoff.
- Local outboxes are not visible to the API. Current-terminal authenticated client must drain ALL local outboxes, detect unresolved states, and explicitly confirm sole-device completeness; the API also checks server prerequisites and uses terminal-locked write barriers. Other copies/devices using the same terminal cannot be proven complete by this architecture; operator must reconcile them before finalization. Late uploads must conflict without deleting their payloads.
- Post-finalization writes to closed periods are blocked; cross-day returns are new adjustment events, not rewrites to old report snapshots. SQL is manual opt-in and retains fiscal history. Tests use disposable in-memory SQLite, never pos_db.

## Work slices

1. Define shared contracts and test business-day boundary/immutable idempotent generation first; implement terminal setup, snapshot model, API service/controller, explicit idempotent SQL deployment.
2. Test event aggregation then implement product/cashier/payment/tax/discount breakdowns, readiness blockers and atomic sequence/snapshot generation.
3. Test finalized-period guards then wire relevant sale/payment/offline/shift/cash/return writers under terminal locking. Preserve idempotent historical ACK before rejecting new late records.
4. Test report HTML then implement thermal formatter, separate printer method, unsupported-platform behavior, persisted print-attempt lifecycle with honest accepted/unknown status.
5. Build supervisor-only New Sales/Cash Drawer navigation into a dedicated Z-Reading page. Check local outboxes before generation, persist retry identity client-side, show readiness/confirmation, recover saved reports after restart and reprint only saved snapshots.
6. Run API/aggregation/formatter/authorization/idempotency tests, existing regression suites, Windows and Android builds, review code and responsive UI fixtures. Document deployment and runtime/printer/PostgreSQL concurrency limits.

No automatic migration, production run, invoice renumbering, counter reset, unrelated refactor, commit, or physical print is authorized.
